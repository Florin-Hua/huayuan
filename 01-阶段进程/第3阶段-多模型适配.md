## 1. 阶段目标

让同一个 AgentCore 和工具系统可以无差别运行在 OpenAI 兼容接口与 Anthropic 原生接口上：

1. 建立供应商中立（provider-neutral）的内部消息格式；
2. 实现 `OpenAIAdapter`，覆盖 OpenAI / DeepSeek / Qwen 等 OpenAI 兼容服务；
3. 实现 `AnthropicAdapter`，支持 Anthropic Messages API 原生 tool_use / tool_result；
4. 增加 provider 工厂，通过 `MODEL_PROVIDER` 或 CLI `--provider` 切换；
5. AgentCore、ReAct 循环、ToolRegistry 不感知具体供应商格式；
6. 用 mock / fixture 验证两个 provider 都能完成同一多步工具任务。

## 3. 核心设计

### 3.1 统一内部格式

MiniAgent 内部继续使用：

- `Message`：`role / content / tool_calls / tool_call_id`
- `ToolCall`：`id / name / arguments`
- `ModelResponse`：`content / tool_calls / usage`
- `Usage`：`prompt_tokens / completion_tokens`

AgentCore 和工具系统只认识以上类型，不认识 OpenAI 或 Anthropic 的原始响应结构。供应商差异被限制在 adapter 层。

### 3.2 OpenAI 兼容适配

`OpenAIAdapter` 负责：

1. 将内部 messages 传给 OpenAI Chat Completions；
2. 解析 `message.tool_calls` 为内部 `ToolCall`；
3. 解析 `usage` 为内部 `Usage`；
4. 对模型返回的非法 JSON arguments 做容错归一化；
5. 通过 `OPENAI_BASE_URL` 支持 DeepSeek、Qwen 等 OpenAI 兼容服务。

### 3.3 Anthropic 原生适配

`AnthropicAdapter` 负责：

| MiniAgent 内部格式 | Anthropic Messages API |
|---|---|
| system message | 独立 `system` 参数 |
| assistant text | assistant 消息中的 `text` content block |
| assistant tool_calls | assistant 消息中的 `tool_use` content block |
| tool result message | user 消息中的 `tool_result` content block |
| OpenAI function schema | Anthropic `name / description / input_schema` |
| `usage.prompt_tokens` | `usage.input_tokens` |
| `usage.completion_tokens` | `usage.output_tokens` |

关键点：

- Anthropic 的 `system` 不是普通 message，必须独立传入；
- `tool_result` 必须放在 user 消息中，并紧跟上一条 assistant `tool_use`；
- 工具 schema 在 MiniAgent 内部继续沿用 OpenAI function 格式，只在 AnthropicAdapter 中转换，避免工具系统出现两套 schema；
- 工具结果中 `ok=False` 会映射为 `is_error=True`，让 Anthropic 明确知道这是失败回喂。

### 3.4 Provider 工厂

```python
provider = settings.model_provider

if provider == "openai":
    return OpenAIAdapter(...)
if provider == "anthropic":
    return AnthropicAdapter(...)
raise ValueError(...)
```

`create_adapter()` 是唯一创建真实 adapter 的入口：

- `MODEL_PROVIDER=openai` → OpenAI / DeepSeek / Qwen 兼容接口；
- `MODEL_PROVIDER=anthropic` → Anthropic 原生接口；
- CLI `--provider` 可临时覆盖 `.env` 配置；
- 未知 provider 直接拒绝，不做静默降级。

### 3.5 配置方式

`.env` 示例：

```env
MODEL_PROVIDER=openai
MODEL_NAME=gpt-4o-mini

OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_API_KEY=sk-your-key

# 切换到 Anthropic：
# MODEL_PROVIDER=anthropic
# MODEL_NAME=claude-sonnet-4-5
# ANTHROPIC_API_KEY=sk-ant-your-key
# ANTHROPIC_BASE_URL=https://api.anthropic.com
# ANTHROPIC_MAX_TOKENS=1024
```

`MODEL_NAME` 是新配置名；旧 `LLM_MODEL` 仍被读取，避免已有配置失效。解析优先级为 `MODEL_NAME` > `LLM_MODEL`。

## 5. 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 架构位置 | provider 差异限制在 adapter 层 | AgentCore、ReAct、工具系统保持稳定，新增 provider 不改核心循环 |
| 统一消息格式 | 内部 `Message/ToolCall/ModelResponse` | 测试和业务层不依赖供应商 SDK 类型 |
| 工具 schema | 内部统一 OpenAI function schema | 工具系统已有实现可复用；Anthropic 转换在 adapter 内完成 |
| Provider 选择 | 配置工厂 + CLI 覆盖 | 适合开发调试，也为后续评测切换模型做准备 |
| 测试方式 | fake client + 录制 fixture | 不访问网络、不消耗 key，能稳定验证协议转换 |
| 真实验收 | 如实标记阻塞 | 不伪造验收数据，网络/key 恢复后补跑 |
