# MiniAgent 与主流 Agent 框架对比

> 对比目的：说明“什么时候应该用框架，什么时候适合自研”，不贬低任何框架。
> 结论先说：MiniAgent 是一个约 3000 行以内、面向学习与个人运行时的小框架；它的价值在于把 ReAct 状态机、工具契约、模型适配、上下文、记忆、护栏和 Trace 的关键取舍亲手实现一遍。若目标是团队生产、复杂多角色编排、深度 human-in-the-loop 或成熟生态集成，优先选择成熟框架。

## 1. 对比总表

| 维度 | MiniAgent | LangGraph | CrewAI | AutoGen | OpenClaw |
|---|---|---|---|---|---|
| 核心抽象 | 手写 ReAct 状态机 + ToolRegistry | StateGraph / 节点 / 条件边 | Crew / Agent / Task / Process | Conversable Agent / GroupChat | 个人助理运行时与工具生态 |
| 定位 | 小型可解释框架 |通用可控工作流编排 | 角色协作任务编排 | 多智能体对话与代码执行 | 产品化个人 Agent / MCP 工具接入 |
| 上下文策略 | 滚动摘要 + 工具输出截断 | 开发者在 state/graph 中管理 | 框架提供部分任务上下文管理 | 会话历史与终止条件 | 面向长期会话与个人运行环境 |
| 持久化 | Trace/Memory 各自 SQLite | checkpoint persistence | 内置存储可选 | 运行时/历史机制依版本演进 | 产品级会话与工具状态 |
| 最大优势 | 每一行都能解释和测试 | 可控性、持久化、human-in-the-loop | 快速组织角色协作 | 灵活的多智能体对话 | 个人助理体验和生态集成 |
| 主要代价 | 生产化功能少 | 概念与调试成本高 | 控制流抽象后不易细调 | 多智能体成本与终止控制复杂 | 与产品运行时和安全边界强绑定 |

## 2. LangGraph：可控工作流编排

LangGraph 的核心抽象是 `StateGraph`：把 Agent 过程建模为共享状态、节点和条件边。它适合需要明确控制流的任务，例如“先检索、再判断是否需要搜索、再生成、最后人工审核”。相比简单链式调用，它的优势在于条件路由、checkpoint persistence、中断恢复、流式输出与状态回放，这些都是生产级长任务的关键能力。

代价是引入一整套图模型和状态约定。状态字段设计、节点边界、边条件、checkpoint schema 都会变成工程负担；调试问题时既要看业务逻辑，也要看图执行框架。MiniAgent 与其差异是：只有一个显式 THINK→ACT→OBSERVE→REFLECT 循环，没有通用图抽象，换取更低的认知成本和更容易的单测覆盖。MiniAgent 目前不提供 checkpoint 恢复，只提供 run 级 Trace 与本地记忆。

## 3. CrewAI：角色协作任务编排

CrewAI 以 `Crew` 组织一组 `Agent` 与 `Task`，通过 sequential 或 hierarchical Process 把任务分配给角色。它擅长快速搭建“研究员 + 写作员 + 审核员”这类多角色协作，角色目标、背景和 expected output 可以直接影响输出风格与分工。

代价是抽象层级较高：任务到底如何被路由、上下文如何传递、失败如何重试，往往被框架约定覆盖。当系统需要精确控制某个工具调用、token 预算或错误回喂时，开发者在框架约定和自定义 hook 之间来回权衡。MiniAgent 没有内置角色系统，多角色只能通过多个 Agent 实例或编排层实现；这牺牲了开箱即用的协作能力，但保留了单循环内的每一步状态、工具结果和护栏语义。

## 4. AutoGen：多智能体对话与代码执行

AutoGen 的代表性抽象是 Conversable Agent 与 GroupChat，让多个具备工具、代码执行或人工输入能力的 Agent 通过消息对话完成任务，并用终止条件控制回合。新版本也向异步 runtime 和更模块化的执行模型演进，适合研究多智能体协商、代码生成-执行-反馈等场景。

它的主要代价是成本与可预测性：多 Agent 对话会放大 token 消耗，若终止条件、发言顺序或角色目标设计不好，任务容易发散。MiniAgent 明确选择单体 Agent，没有 GroupChat 和自动代码执行沙箱。工具参数先经 Pydantic 校验，计算器使用 AST 白名单，文件工具限定沙箱路径，并以最大迭代、token 预算和震荡检测兜底。这是“可解释、可停止”优先于“多智能体涌现能力”的设计取向。

## 5. OpenClaw：产品化个人助理路线

OpenClaw 更接近个人助理运行时产品，而不是一个库：它关注长期会话、个人设备/服务接入、MCP 工具生态、安全审批和权限边界。这类系统的关键问题不只是“能不能调用模型”，而是工具是否可信、敏感操作是否需要用户确认、长期运行状态如何托管、个人数据留在哪里。

它的代价是与产品运行时绑定较深，适合直接使用和二次配置，未必适合作为理解 Agent 内部机制的教材。MiniAgent 选择从最小 CLI 和 Python API 起步，自己实现工具注册、MCP stdio 适配、SQLite Trace/Memory 和错误回喂。MCP server 命令只能由用户在 CLI/配置中显式传入，模型不能自行启动外部进程；这是学习型框架中对权限边界的一次刻意收缩。

## 6. 什么时候不应该自研

- 团队要快速交付多角色工作流：CrewAI / LangGraph 的抽象和生态更合适。
- 需要生产级断点恢复、复杂人工审批、多会话编排：LangGraph 的 persistence 和 interrupt 更完整。
- 研究重点是多智能体协商或自动代码执行：AutoGen 提供了更成熟的实验环境。
- 用户要的是开箱即用的个人助理产品：OpenClaw 一类运行时更接近目标。
- 需要真实浏览器、企业权限、服务托管、并发调度：自研需要大量额外工程。

## 7. 什么时候 MiniAgent 有价值

- 目标是理解 Agent 闭环的每一环，并能向面试官解释设计动机；
- 需要一个小型、可测试、可审计的个人工具运行时；
- 工具集合稳定，主要需求是 ReAct 循环、文件/搜索/计算、MCP 接入；
- 想在固定预算内控制代码复杂度，避免被框架升级和抽象迁移拖住；
- 想为后续研究保留一个可控 baseline，而不是立即追求生产完备。

## 8. 借鉴关系说明

MiniAgent 从零实现，不复制 `04-参考代码/` 或任何商业框架代码。第8阶段的框架对比只用于设计学习：LangGraph 提醒我们持久化和控制流价值；CrewAI 说明角色抽象的生产力；AutoGen 揭示多智能体的成本风险；OpenClaw 强调个人 Agent 的权限与产品化边界。MiniAgent 的实现取舍均在各阶段进程文件中记录。
